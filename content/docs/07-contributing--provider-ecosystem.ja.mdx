---
title: プロバイダーエコシステム
---

この章では、`multicluster-runtime` を取り巻く **プロバイダーエコシステム** がどのように構成されているか、そして **新しいプロバイダーをどのように追加・公開するか** を説明します。

ここでは次の点を学びます。

- 既存のプロバイダーが **どのような種類に分かれているか** と、その現実世界での対応関係
- 新しいプロバイダーを **どこにホストすべきか**（本リポジトリ vs 外部プロジェクト vs 社内専用）
- すべてのプロバイダーに共通する **設計・運用上の期待値**
- 自作プロバイダーを **エコシステムから見つけてもらう方法**

主な対象読者は、独自のインベントリやコントロールプレーンを `multicluster-runtime` と統合したい **プロバイダー作者** および **プラットフォームオーナー** です。

---

### 1. エコシステムにおけるプロバイダーの役割

アーキテクチャ（**Introduction — Architecture** や **Core Concepts — Providers**）で説明したとおり、プロバイダーは次の 2 つの世界の **橋渡し役** です。

- フリート全体を 1 つの概念として扱いたい **Multi-Cluster Manager と Reconciler**
- フリートを表すために現実世界で既に存在している、さまざまな **クラスタ ID / インベントリ / 認証モデル**

`multicluster-runtime` のプロバイダーインターフェースは、あえて非常に小さく保たれています。

- **Discovery（発見）**: いま **どのクラスターがフリートに属しているか**、いつ Ready になったか／離脱したかを把握する。
- **Connectivity（接続）**: 各クラスターに対する `cluster.Cluster`（client / cache / indexer）を構築し、そのライフサイクルを管理する。
- **Indexes（インデックス）**: すべての **Engage 済みクラスター**（現在と将来）のキャッシュにフィールドインデックスを反映する。

この薄いインターフェースの上に、エコシステムは次のような方向に広がります。

- **標準化されたインベントリ**
  - **Cluster API** の `Cluster` リソース
  - **ClusterProfile API**（KEP‑4322）と、その上の Credential プラグイン（KEP‑5339）
  - **About API / ClusterProperty**（KEP‑2149）によるクラスター ID と ClusterSet モデル
- **プラットフォーム固有のインベントリ**
  - マルチテナントコントロールプレーン（例: kcp）
  - クラスタレジストリや SaaS フリートマネージャー
  - クラウドベンダー固有のフリート API（例: Gardener の shoot クラスター）
- **ローカル・疑似フリート**
  - Kind クラスター
  - ファイルシステム上の kubeconfig 群
  - Namespace をクラスターとして見なすシミュレーション

プロバイダーエコシステムとは、これらの統合が実装として存在し、進化し、`multicluster-runtime` 利用者から発見される場所です。

### 2. プロバイダーの種類

大きく分けると、プロバイダーは次の 3 つのカテゴリに分類できます。

- **組み込みリファレンスプロバイダー（本リポジトリ内）**
  - **Kind プロバイダー**: ローカルの Kind クラスター（開発・テスト向け）。
  - **File プロバイダー**: ファイルシステム上の kubeconfig（単一ファイル／ディレクトリ＋glob）。
  - **Kubeconfig プロバイダー**: 管理クラスター内の kubeconfig を含む Secret。
  - **Cluster API プロバイダー**: CAPI の `Cluster` とその kubeconfig Secret。
  - **Cluster Inventory API プロバイダー**: KEP‑4322 の `ClusterProfile` と、KEP‑5339 の Credential プラグイン。
  - **Namespace プロバイダー**: Namespace をクラスターとみなす疑似マルチクラスター。
  - **Multi / Clusters / Single / Nop**: 合成・テスト・ユーティリティ用途のプロバイダー。
  - これらは **リファレンス実装** です。
    - `multicluster.Provider` 実装の具体例を示し、
    - Kubernetes SIG が保守する仕様や API に対応し、
    - 比較的コンパクトで読みやすいコードとして維持されます。

- **関連プロジェクト内のアウトオブツリー・プロバイダー**
  - 別の GitHub 組織／リポジトリにホストされ、そのプロジェクトの近くに置かれます。
  - README で挙げられている例:
    - **kcp-dev/multicluster-provider** — [kcp](https://kcp.io) の論理クラスター向けプロバイダー
    - **gardener/multicluster-provider** — [Gardener](https://gardener.cloud/) の shoot クラスター向けプロバイダー
  - これらのプロバイダーは:
    - 元となるプロジェクトと同じリリースサイクル／互換性ポリシーに従い、
    - プロジェクト固有の依存や前提を自由に持ちつつ、
    - `multicluster.Provider` としてコントローラー作者に統一されたインターフェースを提供します。

- **カスタム／社内専用プロバイダー**
  - エンドユーザーやベンダーが自らの用途で作るプロバイダーです。
    - 自社内のクラスタレジストリやマネージドサービス
    - 独自の DB / REST API / gRPC など
    - 特定の検証・負荷試験用ハーネス
  - 多くの場合、最初は社内リポジトリや組織内のリポジトリで育ちます。
  - 公開しなくても構いませんが、公開する場合は `multicluster-runtime` と連携しやすいように設計できます。

この章の残りでは、「**自分のプロバイダーをどこに置くべきか**」と「**良いプロバイダーとは何か**」に焦点を当てます。

### 3. プロバイダーはどこにホストすべきか

新しいプロバイダーを作る際に最初に決めるべき重要なポイントは、**ホスティング場所** です。

- `kubernetes-sigs/multicluster-runtime` リポジトリの `providers/` 以下に追加するか？
- それとも対象プロジェクトの近くに **別リポジトリとして公開** するか？
- あるいは **社内専用の非公開実装** として運用するか？

#### 3.1 `multicluster-runtime` リポジトリ内のプロバイダー

`multicluster-runtime` プロジェクト自体は **プロバイダーに対して中立** ですが、少数の組み込みプロバイダーを `providers/` 以下に含めています。  
これらは、あくまで **リファレンス実装** や **仕様レベルのサンプル** として位置づけられます。

新しい組み込みプロバイダーを検討する際は、次の質問を自問してください。

- **このプロバイダーは、クロス SIG／仕様レベルの API の「標準実装」になりうるか？**
  - 適している例:
    - Kubernetes SIG が管理する API（ClusterProfile, About API など）の具現化
    - Cluster API のような、既に広く使われている SIG プロジェクトの薄いアダプター
  - 不向きな例:
    - 特定ベンダーやクラウドに深く依存した API やコントロールプレーン
    - すでに独自のリリースサイクルや巨大なコードベースを持つプラットフォーム

- **プロバイダーを小さく・明確なスコープに保てるか？**
  - 組み込みプロバイダーは:
    - 役割が明確で、
    - プラットフォーム固有の巨大な依存を引き込まず、
    - SIG-Multicluster のメンテナーが継続的にレビュー・保守できる規模であることが望まれます。

- **メンテナーが明確に存在するか？**
  - `providers/<name>` 以下には:
    - レビューア／アプローバーを示す `OWNERS` ファイルがあり、
    - コアの API 変更に追従するテストが整備され、
    - CI（`make test` / envtest / lint）で継続的に検証されている必要があります。

もしあなたのプロバイダーが:

- **Kubernetes 全体で意味を持つ概念** を扱っており、
- 複数のプロジェクトにまたがって再利用可能で、
- SIG-Multicluster コミュニティで保守可能なスコープであれば、

KEP などの仕様に対する **リファレンス実装** として in-tree プロバイダーを提案する価値があります。

#### 3.2 外部プロジェクト内のプロバイダー

多くの統合にとって、最も自然な場所は **インベントリやコントロールプレーン本体のリポジトリ** です。  
これは、次のようなプロジェクトが採用しているパターンです。

- `kcp-dev/multicluster-provider`（kcp 向け）
- `gardener/multicluster-provider`（Gardener shoot 向け）

プロバイダーを外部プロジェクト側にホストするのが適しているのは、たとえば次のような場合です。

- **対象プロジェクトが独自のリリースサイクルと互換性ポリシーを持っている**
  - プロバイダーを次と同じ単位でバージョニングしたい場合:
    - CRD スキーマ
    - コントロールプレーン API
    - クラウド固有の挙動や依存

- **プロバイダーがそのプロジェクト固有の API やライブラリに依存している**
  - 例:
    - Kubernetes SIG 以外が提供する CRD セット
    - ベンダー独自の SDK やクライアント

- **そのプロジェクトのメンテナーが自然なオーナーである**
  - API の長期的な進化を理解しており、
  - 自身のエコシステムの中でテストやドキュメントを整備しやすい。

この場合でも、`multicluster-runtime` との統合面は共通です。

- 公開 Go モジュールとして `multicluster.Provider` を実装する。
- ドキュメントで:
  - プロバイダーの構築方法とオプション
  - `mcmanager.New` への組み込み方
  - 必要な CRD・RBAC・ブートストラップ手順
  を説明する。

プロバイダーがある程度安定したら、本リポジトリに対して小さな PR を送り、  
README の **Provider Ecosystem** セクションにリンクを追加すると、ユーザーから発見されやすくなります。

#### 3.3 カスタム／社内専用プロバイダー

すべてのプロバイダーを公開する必要はありません。

たとえば次のような運用も、完全にサポートされています。

- プロバイダーを社内のインフラとしてのみ利用し、公開しない。
- **Custom Providers** の章と `pkg/clusters.Clusters` のヘルパーを活用して実装する。
- 自分たちの API やプラットフォームの背後に隠蔽し、利用者には `ClusterName` だけを意識させる。

コードを公開しない場合でも、次のような関わり方が可能です。

- 自分たちのプラットフォームから `multicluster-runtime` をどう使うかをドキュメント化する。
- Provider 実装で見つけた問題や改善点を、コアライブラリ側へ Issue/PR として還元する。
- 将来的な相互運用を見据えて、クラスター ID / インベントリ / 認証のモデルを KEP 群（KEP‑2149 / 4322 / 5339）に揃えておく。

### 4. すべてのプロバイダーに共通する期待値

どこにホストされているかに関わらず、プロバイダーにはいくつかの **共通した期待事項** があります。  
これらを満たしていると、コントローラーからの利用や障害調査がはるかに行いやすくなります。

#### 4.1 API とセマンティクス

- **コアインターフェースを正しく実装する**
  - `multicluster.Provider`
    - `Get(ctx, clusterName)` は:
      - 既知のクラスター名に対して `cluster.Cluster` を返す。
      - 不明または離脱済みのクラスターに対して `multicluster.ErrClusterNotFound` を返す。
    - `IndexField(ctx, obj, field, extract)` は:
      - 現在 Engage 済みのすべてのクラスターにインデックスを適用し、
      - 将来追加されるクラスターにも同じインデックスが適用されるように保存する。
  - `multicluster.ProviderRunnable`（必要な場合）
    - `Start(ctx, aware)` は:
      - プロバイダーのライフタイム中ブロックし続ける長時間処理である。
      - 準備ができたクラスターに対して `aware.Engage(clusterCtx, name, cluster)` を呼び出す。
      - `ctx.Done()` を尊重して終了する。

- **ID と Ready 判定のセマンティクスを明確にする**
  - クラスター名（`ClusterName`）は:
    - クラスターのライフタイム（少なくとも ClusterSet 所属期間）の間、**安定している** べきです。
    - プロバイダーのドメイン内で **一意** であるべきです。
  - 可能であれば、クラスター ID を次と整合させます。
    - **KEP‑2149（ClusterId）** の `ClusterProperty`（`cluster.clusterset.k8s.io` など）
    - KEP‑4322 の `ClusterProfile.status.properties` に格納された ID など
  - Ready 判定条件を明示します。
    - 例: CAPI `Cluster` の `Status.Phase == Provisioned`
    - 例: `ClusterProfile.status.conditions["ControlPlaneHealthy"] == True`

- **ライフサイクルを決定的に管理する**
  - クラスターごとに:
    - 専用のコンテキスト（`clusterCtx`）を作り、フリートから外れたタイミングでキャンセルする。
    - キャッシュを起動し、`WaitForCacheSync` が完了してから `Engage` を呼ぶ。
    - クラスター削除後に `ErrClusterNotFound` が返ることを前提とした Reconciler の実装を尊重する。

#### 4.2 テスト

- **ユニットテスト**
  - 次のような点をテストします。
    - インベントリの変化 → `AddOrReplace` / `Remove` へのマッピング
    - `Get` / `IndexField` の挙動
    - 無効な kubeconfig や認証情報欠落などのエッジケース

- **統合テスト**
  - Kubernetes API をインベントリとして利用する場合は、envtest によるスイートを構築します。
    - ローカル API Server を起動し、
    - 必要な CRD（CAPI, ClusterProfile など）をインストールし、
    - Provider の Reconcile ループを end-to-end で検証する。

- **Examples を「動くドキュメント」として整備する**
  - `examples/<provider-name>` のような小さなモジュールを用意し、次を示します。
    - プロバイダーを Multi-Cluster Manager に組み込む方法
    - 具体的なマルチクラスターコントローラーの一例
  - `hack/check-everything.sh` 相当の仕組みで、これらの example がビルドされ続けるようにします。

#### 4.3 セキュリティと認証情報

- **コントローラーコードに認証情報を埋め込まない**
  - プロバイダーは次のような仕組みで `*rest.Config` を取得すべきです。
    - kubeconfig ファイル／Secret
    - Credential プラグイン（KEP‑5339）や Workload Identity
    - クラウドネイティブな ID 連携
  - トークンや秘密鍵を Go コードに直接埋め込むのではなく、`ClusterProfile` やプラグイン、外部設定ファイル／Secret に委譲します。

- **認証情報のローテーションを前提にする**
  - 認証情報をローテーションしても `ClusterName` が変わらないように設計します。
  - 例:
    - Kubeconfig プロバイダー: kubeconfig Secret の変更を検知し、必要に応じて `cluster.Cluster` を再生成する。
    - Cluster Inventory API プロバイダー: 新旧 kubeconfig を比較し、必要なときだけクラスターを作り直す。

#### 4.4 可観測性

- **ログ**
  - 重要なログには必ず `clusterName`（および可能なら ClusterSet ID）を含めるようにします。

- **メトリクス**
  - 次のような問いに答えられるメトリクスを用意すると便利です。
    - 「いま Engage されているクラスターはどれか？」
    - 「このプロバイダーが作成／更新／削除したクラスターはどれくらいか？」
    - 「インベントリ／認証／接続まわりで、どのようなエラーが多いか？」

- **ドキュメント**
  - 次を明確に記述します。
    - 必要な CRD・Secret・外部依存
    - オプションとデフォルト値
    - 典型的な障害モードとトラブルシュート方法

### 5. プロバイダーをエコシステムにコントリビュートする

プロバイダーをエコシステムに参加させる方法は大きく 2 つあります。

- **アウトオブツリー・プロバイダーとして公開する**
- **新しい in-tree プロバイダーとして提案する**

#### 5.1 アウトオブツリー・プロバイダーを公開する

プロバイダーを独立したリポジトリ（または対象プロジェクトのリポジトリ）に置く場合でも、`multicluster-runtime` ユーザーにとって使いやすい形で公開できます。

- **1. API を安定させる**
  - Go パッケージとして次を公開します。
    - コンストラクタ（例: `func New(opts Options) (*Provider, error)`）
    - `multicluster.Provider`（と必要なら `ProviderRunnable`）を実装する型
    - 設定用の `Options` 構造体

- **2. ドキュメントを用意する**
  - 最低限、README などで次を説明します。
    - 必要な CRD や追加コントローラーのインストール手順
    - プロバイダーの構築方法と `mcmanager.New` への組み込み方
    - インベントリ（どのリソースがクラスターを表すか）と認証方法
    - クラスター名と Ready 判定のセマンティクス

- **3. README の「Provider Ecosystem」リストに追記する**
  - `kubernetes-sigs/multicluster-runtime` に対して小さな PR を送り:
    - ルート `README.md` の **Provider Ecosystem** セクションに、
    - あなたのリポジトリへのリンクと短い説明を追加します。
  - これが最も軽量な統合方法で、リリースサイクルを結合せずに discoverability を高められます。

#### 5.2 新しい in-tree プロバイダーを提案する

もし「このプロバイダーは `multicluster-runtime` リポジトリ内にあるべきだ」と考える場合は、次のステップを踏むことをおすすめします。

- **1. まず設計レベルの議論を行う**
  - `kubernetes-sigs/multicluster-runtime` に Issue や Discussion を立て、次を説明します。
    - 解決したいユーザーストーリーと、その汎用性
    - 既存の KEP や SIG が定義した API との関係
    - 想定している配置場所（例: `providers/<name>`）
  - 仕様レベルの機能であれば、関連 SIG に対する KEP が必要になる場合もあります。

- **2. 独立したモジュールとして実装する**
  - `providers/<name>` を作成し、次を含めます。
    - 独自の `go.mod` / `go.sum`
    - `OWNERS` ファイル
    - テストと（可能なら）`examples/<name>` 以下の example
  - 既存の in-tree プロバイダー（`cluster-api`, `cluster-inventory-api`, `kubeconfig`, `file`, `kind` など）と同じパターンに従います。

- **3. ドキュメントとツールチェーンに統合する**
  - 次を追加します。
    - `docs/05-providers-reference--<name>-provider.md` に **Providers Reference** 章
    - 必要に応じて:
      - **Core Concepts — Providers**
      - 関連する **Advanced Topics** への参照
  - そして:
    - `make test`
    - `make lint`
    - `make verify-modules`
    がすべて通ることを確認します。

- **4. レビューとフィードバックを繰り返す**
  - レビューでは次のような点が議論されることが多いです。
    - API 形状と controller-runtime との一貫性
    - KEP や SIG のスコープとの整合性
    - テストカバレッジと障害時の挙動
  - Provider の実装は比較的大きくなりがちなので、型定義／コントローラー配線／テスト／ドキュメントなど、複数の PR に分割するのもよい戦略です。

### 6. エコシステム統合の具体例

現在のエコシステムは、いくつかの代表的な統合パターンを既に体現しています。

- **仕様駆動の in-tree リファレンス**
  - **Cluster Inventory API プロバイダー**
    - 本リポジトリ内に実装されており、
    - KEP‑4322 の ClusterProfile API と KEP‑5339 の Credential プラグインに準拠したリファレンス実装です。
  - **Cluster API プロバイダー**
    - 本リポジトリ内に実装されており、
    - SIG-Cluster-Lifecycle が管理する CAPI `Cluster` リソースをインベントリとして利用します。

- **アウトオブツリーかつプロジェクト所有のプロバイダー**
  - **kcp-dev/multicluster-provider**
    - kcp リポジトリの近くにホストされ、
    - kcp のリリース・互換性ポリシーに従います。
  - **gardener/multicluster-provider**
    - Gardener 組織の下にホストされ、
    - Gardener の shoot クラスターをフリートとして `multicluster-runtime` に公開します。

これらの例は、「自分のプロバイダーをどこに置くべきか」「どの程度プラットフォームと結合させるべきか」を考える際の良いテンプレートになります。

---

### 7. 次のステップ

プロバイダーを設計・実装しようとしている場合は、次のドキュメントやコードを読むとよいでしょう。

- Providers Reference の **Custom Providers** 章  
  実装パターン（`pkg/clusters.Clusters` を使った実装など）が詳しく解説されています。
- 既存の組み込みプロバイダーのコード  
  自分のユースケースに最も近いものを 1〜2 個選び、どのように `multicluster.Provider` を実装しているかを読むと理解が深まります。
- ID / インベントリ / Credential モデルに関する KEP
  - **KEP‑2149（ClusterProperty / ClusterId / ClusterSet）**
  - **KEP‑4322（ClusterProfile API）**
  - **KEP‑5339（Credentials Plugin）**

プロバイダーがある程度使える状態になったら、次のいずれか、あるいは両方を検討してください。

- 独立モジュールとして公開し、README の **Provider Ecosystem** セクションにリンクを追加する。
- もし仕様レベル・クロス SIG な位置づけであれば、本章のガイドラインに従って新しい in-tree プロバイダーとして提案する。

いずれの形であれ、一貫したセマンティクス・十分なテスト・明快なドキュメントを備えたプロバイダーは、あなた自身にとってもコミュニティにとっても扱いやすく、`multicluster-runtime` エコシステムの中で長く活躍できる存在になります。
