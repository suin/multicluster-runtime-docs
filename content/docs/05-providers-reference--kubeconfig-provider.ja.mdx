---
title: Kubeconfig Provider
---

**Kubeconfig Provider** は、Kubernetes クラスター上の **kubeconfig を含む Secret** からクラスターを自動検出し、それぞれに対して `cluster.Cluster` を生成して **Multi-Cluster Manager** に Engage するプロバイダーです。  
Kind や Cluster API のような専用インベントリを前提にする代わりに、「この Secret が 1 クラスター」を意味するというシンプルなモデルを採ります。

Kubeconfig Provider はおおまかに次のことを行います。

- **Secret を監視する**:
  - 単一 Namespace 内の Secret を watch し、
  - 特定のラベル（デフォルトでは `sigs.k8s.io/multicluster-runtime-kubeconfig: "true"`）が付いているものだけを対象とします。
- **Secret から kubeconfig を取り出す**:
  - Secret の `data` にある特定キー（デフォルトでは `kubeconfig`）から kubeconfig バイト列を取得します。
- **`cluster.Cluster` を生成して起動する**:
  - kubeconfig を `*rest.Config` に変換し、`cluster.New` でクラスターオブジェクトを作ります。
- **Multi-Cluster Manager に Engage する**:
  - Secret 名を `ClusterName` として Multi-Cluster Manager に渡し、マルチクラスターコントローラーが利用できるようにします。

Provider の全体像については「**コアコンセプト — プロバイダー**」(`03-core-concepts--providers.md`) を参照してください。  
ここでは、Kubeconfig Provider 固有の設定方法・動作・ユースケースに絞って解説します。

---

### Kubeconfig Provider を使うべき場面

次のような状況では、Kubeconfig Provider を選ぶのが適しています。

- **インベントリが「kubeconfig のリスト」で表現されている**
  - すでに各クラスターの kubeconfig を持っている。
  - それらを管理クラスター上の Secret として配置できる。
- **クラスターを少しずつフリートに追加したい**
  - 新しい Secret を 1 つ作るだけでクラスターを追加できる。
  - Secret を削除すれば、そのクラスターはフリートから外れる。
- **シンプルで明示的なモデルを好む**
  - 追加の CRD（`ClusterProfile` や CAPI `Cluster`）を導入せずに始めたい。
  - クレデンシャルの範囲や権限を kubeconfig ごとに明示的に設計したい。

一方で、次のような場合は他の Provider の方が自然です。

- **Cluster Inventory API / ClusterProfile でクラスタインベントリを表現している**
  - → KEP‑4322/KEP‑5339 と整合する **Cluster Inventory API Provider** を推奨。
- **クラスターライフサイクル管理に Cluster API を使っている**
  - → CAPI `Cluster` と kubeconfig Secret を直接読む **Cluster API Provider** が適しています。
- **ローカル開発やテストがメイン**
  - → Kind クラスターに特化した **Kind Provider** の方が手軽です。
- **ファイルシステム上の kubeconfig ファイルを直接使いたい**
  - → Secret ではなくファイルを読む **File Provider** が適しています。

ClusterProfile KEP（KEP‑4322/KEP‑5339）でいうところの **「Secret による Push モデル（本番利用は非推奨）」** に相当する設計であり、シンプルで分かりやすい反面、「長寿命 kubeconfig Secret」を運用することのセキュリティ／ローテーション上の注意が必要です。

### トポロジー: Kubeconfig Provider が収まる位置

典型的な構成は次のようになります。

- **管理クラスター**
  - マルチクラスターコントローラーが動作するコントロールプレーン。
  - 各メンバークラスターへの kubeconfig を格納した Secret をホストする。
  - **Multi-Cluster Manager**（`mcmanager.Manager`）と Kubeconfig Provider が動作する。
- **メンバークラスター**
  - どのような Kubernetes クラスターでも構わない（クラウド、オンプレ、マネージド問わず）。
  - 各クラスターに、コントローラー用の ServiceAccount / ID と RBAC が設定されている。
  - その ID でアクセスできる kubeconfig を、管理クラスター上の Secret にエクスポートしておく。

Kubeconfig Provider 自体は **別プロセスではなくライブラリ** です。

- `main.go` 内で Go の値として生成され、
- `mcmanager.New(...)` に Provider として渡され、
- `mgr.GetLocalManager()` を使ってローカルマネージャー上に Secret 用 Controller を登録し、
- `mgr.Start(ctx)` を呼ぶことで、Multi-Cluster Manager とともに起動します。

Reconciler から見ると、他の Provider と違いはありません。

- `mcreconcile.Request.ClusterName` に **Secret 名** が入り、
- `mgr.GetCluster(ctx, req.ClusterName)` で、その Secret 由来の `cluster.Cluster` を取得します。

### 設定: `kubeconfig.Options`

Kubeconfig Provider の実装は `providers/kubeconfig/provider.go` にあり、次のように構築します。

```go
import kubeconfig "sigs.k8s.io/multicluster-runtime/providers/kubeconfig"

provider := kubeconfig.New(kubeconfig.Options{
  Namespace:             "default",
  KubeconfigSecretLabel: "sigs.k8s.io/multicluster-runtime-kubeconfig",
  KubeconfigSecretKey:   "kubeconfig",
})
```

`Options` は Secret の検出方法と `rest.Config` / `cluster.Cluster` の構築方法を制御します。

```go
type Options struct {
  // Namespace is the namespace where kubeconfig secrets are stored.
  Namespace string
  // KubeconfigSecretLabel is the label used to identify secrets containing kubeconfig data.
  KubeconfigSecretLabel string
  // KubeconfigSecretKey is the key in the secret data that contains the kubeconfig.
  KubeconfigSecretKey string
  // ClusterOptions is the list of options to pass to the cluster object.
  ClusterOptions []cluster.Option
  // RESTOptions is the list of options to pass to the rest client.
  RESTOptions []func(cfg *rest.Config) error
}
```

デフォルト値:

- `KubeconfigSecretLabel` が空の場合、  
  `sigs.k8s.io/multicluster-runtime-kubeconfig` が使われます。
- `KubeconfigSecretKey` が空の場合、`kubeconfig` が使われます。

各フィールドの意味:

- **`Namespace`**
  - この Namespace 内の Secret だけが対象になります。
  - 典型的には専用 Namespace（例: `multicluster-kubeconfigs`）を用意し、RBAC でアクセスを限定します。
- **`KubeconfigSecretLabel`**
  - このラベルキーが `"true"` の Secret だけを watch / Reconcile 対象とします。
  - 同じ Namespace に別用途の Secret があっても、誤ってクラスターとして扱われることを防げます。
- **`KubeconfigSecretKey`**
  - kubeconfig バイト列が格納されている `data` のキーです。
  - キーが存在しない・空の場合、その Secret はログを出してスキップされます。
- **`ClusterOptions`**
  - `cluster.New(restConfig, ...)` に渡されるオプションを指定します。
  - 例:
    - Scheme の追加登録
    - Cache や Client の設定（レートリミットなど）
    - メトリクスやヘルスチェックの設定
- **`RESTOptions`**
  - 生成された `*rest.Config` に対して任意の変更を行う関数のリストです。
  - 例:
    - QPS / Burst のチューニング
    - User-Agent の付与
    - TLS の詳細設定

テスト（`kubeconfig_suite_test.go`）では、これらのフィールドを非デフォルト値で指定したケースがカバーされており、期待どおりに反映されることが確認されています。

### Secret の構造とクラスター名

Kubeconfig Provider は、条件に合致する **各 Secret を 1 つのクラスター** とみなします。

デフォルトでは、次の条件を満たす Secret がクラスターとして扱われます。

- `Options.Namespace` 内に存在すること
- メタデータラベルに `<KubeconfigSecretLabel>: "true"` を持つこと
- `data[<KubeconfigSecretKey>]` に kubeconfig バイト列を持つこと

**クラスター名 (`ClusterName`)** は、その Secret の **名前** そのものです。

- コントローラーが受け取る `mcreconcile.Request.ClusterName` にこの文字列が入ります。
- この Provider と Namespace の中だけで一意であればよく、グローバルなクラスター ID とは独立した概念です（グローバル ID が必要な場合は、KEP‑2149 の About API / `ClusterProperty` などと組み合わせてください）。

デフォルト設定を使った最小限の Secret 例は次のようになります。

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: cluster-a
  namespace: multicluster-kubeconfigs
  labels:
    sigs.k8s.io/multicluster-runtime-kubeconfig: "true"
data:
  kubeconfig: <base64-encoded kubeconfig>
```

この Secret は、`ClusterName = "cluster-a"` のクラスターとして Multi-Cluster Manager に現れます。

利用者側の責務としては、次の点を意識してください。

- Secret 名は Namespace 内で一意にする。
- kubeconfig の内容が、意図した 1 つのクラスターを指していること（複数コンテキストを含む kubeconfig を使う場合は、とくに注意）。
- kubeconfig に含まれるクレデンシャルの RBAC が、メンバークラスター側で最小権限になるよう設計すること。

より構造化されたインベントリ（`ClusterProfile` など）をすでに持っている場合は、Secret を直接管理するかわりに **Cluster Inventory API Provider** を使う方が、スケールやセキュリティの観点で有利です。

### ディスカバリと Engage の仕組み

Kubeconfig Provider は次の 2 つの役割を持ちます。

- `multicluster.Provider` の実装（`Get` / `IndexField`）
- `controller-runtime` の `Reconciler` としての Secret コントローラー

ディスカバリは `SetupWithManager` から始まります。

```go
func (p *Provider) SetupWithManager(ctx context.Context, mgr mcmanager.Manager) error
```

`SetupWithManager` は次の処理を行います。

- 渡された `mcmanager.Manager` を内部に保存する。
- `mgr.GetLocalManager()` でローカルマネージャーを取得する。
- そのローカルマネージャー上に Secret 用 Controller を登録する:
  - `For(&corev1.Secret{}, ...)`
  - `Options.Namespace` と `Options.KubeconfigSecretLabel` によるフィルタを付ける。

その後、ローカルマネージャーと Multi-Cluster Manager が起動すると、Secret の変更が Reconcile ループを通じてクラスターの追加・更新・削除に反映されます。

#### Secret の Reconcile ループ

中心となるロジックは `Reconcile(ctx, req)` にあります。

1. **Secret の取得**
   - ローカルマネージャーの Client を使って `req.NamespacedName` の Secret を `Get` する。
   - 見つからない場合（`IsNotFound`）:
     - `removeCluster(req.Name)` を呼び出し、該当クラスターを内部マップから削除し、専用コンテキストをキャンセルする。
     - 正常終了として返す。
2. **削除中 Secret の扱い**
   - `secret.DeletionTimestamp` が非 `nil` の場合:
     - 同様に `removeCluster(clusterName)` を呼び、クラスターをフリートから外す。
3. **kubeconfig バイト列の取り出し**
   - `secret.Data[Options.KubeconfigSecretKey]` を参照する。
   - キーが存在しない・空の場合:
     - 「kubeconfig がないのでスキップ」とログ出力し、何もしないで終了する。
4. **ハッシュによる変更検知**
   - kubeconfig バイト列に対して SHA‑256 ハッシュを計算する。
   - 同名クラスターが既に存在し、保存済みハッシュと一致する場合:
     - 「同じ kubeconfig を持つクラスターが既に存在するのでスキップ」とログ出力し、終了。
   - 同名クラスターが存在するがハッシュが異なる場合:
     - 「クラスターを更新する」とログ出力し、`removeCluster(clusterName)` で既存クラスターを停止・削除する。
5. **クラスターの生成と Engage**
   - `createAndEngageCluster(ctx, clusterName, kubeconfigData, hashStr, log)` を呼び出す。
   - この中で:
     - `clientcmd.RESTConfigFromKubeConfig` で kubeconfig を `*rest.Config` に変換。
     - `Options.RESTOptions` を順に適用。
     - `cluster.New(restConfig, Options.ClusterOptions...)` で `cluster.Cluster` を生成。
     - これまで登録されていた Field Index を新しいクラスターの Cache に適用。
     - `context.WithCancel(ctx)` でクラスター専用コンテキストを作成し、`cl.Start(clusterCtx)` をゴルーチンで起動。
     - `mgr.Engage(clusterCtx, clusterName, cl)` を呼び出して Multi-Cluster Manager に登録。
     - `cl.GetCache().WaitForCacheSync(clusterCtx)` で Cache 同期完了を待つ。
     - 最後に、クラスター本体・コンテキスト・キャンセル関数・ハッシュを内部マップに保存する。

内部状態（クラスターのマップや Indexer のリスト）はすべて RW ミューテックスで保護されており、

- `Get` や `ListClusters` などの読み取りは read ロック、
- `setCluster` / `removeCluster` / Indexer 追加などの更新は write ロック、

を使ってレースコンディションを避けています（`Provider race condition` のテストで検証されています）。

この設計により:

- **Secret の作成** → 新しいクラスターが生成・Engage される。
- **Secret の更新** → kubeconfig が変化していれば、クラスターを作り直して再 Engage する。
- **Secret の削除** → クラスターがフリートから外れ、専用コンテキストがキャンセルされる。

#### `Get` と `IndexField`

Provider は `multicluster.Provider` インターフェースを次のように実装しています。

- `Get(ctx, clusterName)`:
  - 内部マップから名前で検索し、
  - 見つからなければ `multicluster.ErrClusterNotFound` を返す。
  - 見つかれば `cluster.Cluster` を返す。
- `IndexField(ctx, obj, field, extractValue)`:
  - 引数 `(obj, field, extractValue)` を `indexers` スライスに保存し（将来のクラスター向け）、
  - すでに存在するすべてのクラスターの Cache に対して直ちに `IndexField` を適用する。

これは他の Provider と同様に、

- コントローラー側は `mgr.GetFieldIndexer().IndexField(...)` を **起動時に 1 回だけ** 呼べばよく、
- Provider 側が「既存クラスターと将来追加されるクラスターの両方」にインデックス定義を反映する、

という契約を満たします。

### 利用例: end-to-end のセットアップ

`examples/kubeconfig/main.go` には、Kubeconfig Provider を使った一連の手順がまとまったサンプルがあります。ここではその流れを要約します。

1. **フラグとロガーの設定**

   ```go
   var namespace, kubeconfigSecretLabel, kubeconfigSecretKey string

   flag.StringVar(&namespace, "namespace", "default", "Namespace where kubeconfig secrets are stored")
   flag.StringVar(&kubeconfigSecretLabel, "kubeconfig-label", "sigs.k8s.io/multicluster-runtime-kubeconfig",
     "Label used to identify secrets containing kubeconfig data")
   flag.StringVar(&kubeconfigSecretKey, "kubeconfig-key", "kubeconfig",
     "Key in the secret data that contains the kubeconfig")
   // zap ロガーの初期化など
   ```

2. **Kubeconfig Provider の生成**

   ```go
   providerOpts := kubeconfigprovider.Options{
     Namespace:             namespace,
     KubeconfigSecretLabel: kubeconfigSecretLabel,
     KubeconfigSecretKey:   kubeconfigSecretKey,
   }
   provider := kubeconfigprovider.New(providerOpts)
   ```

3. **Multi-Cluster Manager の生成**

   ```go
   mgr, err := mcmanager.New(ctrl.GetConfigOrDie(), provider, mcmanager.Options{
     Metrics: metricsserver.Options{
       BindAddress: "0", // この例ではメトリクスサーバーを無効化
     },
   })
   ```

4. **Provider のコントローラーを Manager に登録**

   ```go
   if err := provider.SetupWithManager(ctx, mgr); err != nil {
     // エラーハンドリング
   }
   ```

5. **マルチクラスターコントローラーの登録**

   ```go
   if err := mcbuilder.ControllerManagedBy(mgr).
     Named("multicluster-configmaps").
     For(&corev1.ConfigMap{}).
     Complete(mcreconcile.Func(
       func(ctx context.Context, req mcreconcile.Request) (ctrl.Result, error) {
         log := ctrllog.FromContext(ctx).WithValues("cluster", req.ClusterName)
         log.Info("Reconciling ConfigMap")

         cl, err := mgr.GetCluster(ctx, req.ClusterName)
         if err != nil {
           return reconcile.Result{}, err
         }

         cm := &corev1.ConfigMap{}
         if err := cl.GetClient().Get(ctx, req.Request.NamespacedName, cm); err != nil {
           if apierrors.IsNotFound(err) {
             return ctrl.Result{}, nil
           }
           return ctrl.Result{}, err
         }

         log.Info("ConfigMap found", "namespace", cm.Namespace, "name", cm.Name, "cluster", req.ClusterName)
         return ctrl.Result{}, nil
       },
     )); err != nil {
     // エラーハンドリング
   }
   ```

6. **Manager の起動**

   ```go
   if err := mgr.Start(ctx); err != nil && !errors.Is(err, context.Canceled) {
     // エラーハンドリング
   }
   ```

実行時の挙動:

- 管理クラスター上で、メンバークラスターごとに 1 つの Secret を作成します。
- Provider がそれらの Secret を検出し、クラスターを生成・Engage します。
- コントローラーは `mcreconcile.Request` を通じて、各クラスター／各リソースのイベントを受け取ります。
- Secret の削除や更新によって、フリートからクラスターを外したり、クレデンシャルをローテーションしたりできます。

メンバークラスター側の ServiceAccount／RBAC を含めたセットアップの実例や、kubeconfig Secret を自動で作成するスクリプトは、`examples/kubeconfig/README.md` と `examples/kubeconfig/scripts/create-kubeconfig-secret.sh` にまとまっています。

### Field Index の挙動

Kubeconfig Provider は、他の Provider と同様に Field Index を扱います。

- コントローラー側が `mgr.GetFieldIndexer().IndexField(...)` を呼ぶと、
  - Multi-Cluster Manager はそれを Provider の `IndexField` に委譲します。
- Provider 側では:
  - インデックス定義（`object`, `field`, `extractValue`）を内部スライスに保存し（将来のクラスター向け）、
  - 現在 Engage 済みのすべてのクラスターに対してただちに `IndexField` を適用します。

新しいクラスターが Secret から生成される際には、

- `createAndEngageCluster` の中で `applyIndexers` が呼ばれ、
- 既存のインデックス定義がクラスターの Cache に適用されたあとで `Engage` されます。

そのため、利用者側のベストプラクティスは次のとおりです。

- アプリケーション起動時に一度だけ `IndexField` を登録する。
- どのタイミングで Secret が追加されても、すべてのクラスターで同じインデックスが利用できると仮定してよい。

### セキュリティと RBAC の考慮事項

セキュリティ上は、**管理クラスター** と **メンバークラスター** の 2 つの面を考える必要があります。

**管理クラスター側**:

- コントローラーポッドの ServiceAccount には、少なくとも次の権限が必要です。
  - `Options.Namespace` 内の Secret に対する `get`, `list`, `watch`
  - ラベル付き kubeconfig Secret の読取権限
- `examples/kubeconfig` のスクリプトを利用する場合:
  - メンバークラスター上で ServiceAccount / Role / RoleBinding / ClusterRoleBinding を作成し、
  - 管理クラスター側に、期待どおりのラベル・キーを持つ kubeconfig Secret を作成します。

**メンバークラスター側**:

- 各 Secret に含まれる kubeconfig の権限が、そのままコントローラーの権限になります。
  - 本番環境では、クラスターごと・コントローラーごとに **最小権限** の ServiceAccount を用意するのが望ましいです。
  - 可能であれば短寿命トークンや Workload Identity などを使って、ローテーションしやすい形にします。
- Provider は kubeconfig の内容を変更せず `rest.Config` に変換するだけなので、
  - RBAC の過不足や誤設定はそのままコントローラーに反映されます。

KEP‑5339（Credential Plugin モデル）との関係:

- Kubeconfig Provider は、ClusterProfile の `credentialProviders` や Exec Plugin を使うのではなく、**静的 kubeconfig Secret** を前提としています。
- よりセキュアな運用やクレデンシャルローテーションを重視する場合は、
  - ClusterProfile + Credential Plugin に基づく **Cluster Inventory API Provider** の採用、
  - もしくは外部仕組みによる Secret 自体の自動ローテーション、
  を検討してください。

### 運用ノートとトラブルシューティング

いくつか代表的な挙動と、その見方・対処方法を挙げます。

- **クラスターが `ListClusters` / `GetCluster` に現れない**
  - 次の点を確認してください。
    - Secret が `Options.Namespace` に存在するか。
    - Secret に正しいラベルキー／値が付与されているか。
    - `data[Options.KubeconfigSecretKey]` に kubeconfig バイト列が入っているか。
  - `kubeconfig-provider` ロガーの出力を確認し、kubeconfig パースエラーや RBAC エラーが出ていないか確認します。

- **Reconciler が `ErrClusterNotFound` を受け取る**
  - 次のいずれかの状況が考えられます。
    - 該当 Secret がもともと存在しない。
    - Secret が削除されたあとに、そのクラスター向けのイベントがキューに残っていた。
    - Secret はあるが、Provider がまだクラスターを Engage できていない（kubeconfig エラーなど）。
  - `mcbuilder` で作ったコントローラーのデフォルトラッパーでは、このエラーを **非致命的** とみなし、再キューを行わないようになっています。

- **Secret を更新しても、古いクレデンシャルのままに見える**
  - Provider は kubeconfig バイト列のハッシュで変更を検知します。
    - バイト列が変化した場合:
      - 既存クラスターを削除し、新しい `cluster.Cluster` を作り直して再 Engage します。
    - kubeconfig 以外（アノテーションや別の data キー）だけが変化した場合:
      - ハッシュは変わらず、クラスターは再利用されます。
  - kubeconfig を変更したのに挙動が変わらない場合は:
    - 実際に kubeconfig バイト列が変わっているか（コンテキストやトークンが変わっているか）を確認し、
    - Provider のログにエラーが出ていないか確認してください。

- **多数のクラスターを頻繁に出し入れする**
  - Secret の作成／削除ごとに `cluster.Cluster` の生成・停止と Cache の起動・終了が行われます。
  - 規模が大きく、クラスターの churn が激しい環境では、
    - ClusterProfile ベースのインベントリや、
    - `pkg/clusters.Clusters` を用いた Provider
    のような、よりスケールに配慮した実装を検討してください。

---

### まとめ

Kubeconfig Provider は、**kubeconfig を含む Secret** と `multicluster-runtime` のフリートモデルの間をつなぐ、シンプルで分かりやすいブリッジです。  
ラベル付き Secret ごとに `cluster.Cluster` を生成し、Secret 名を `ClusterName` として Engage することで、既存の kubeconfig 運用をほぼそのまま活かしつつマルチクラスターコントローラーを構築できます。  
将来的に ClusterProfile や Credential Plugin（KEP‑4322 / KEP‑5339）へ移行する場合でも、Reconciler 側は `ClusterName` と `GetCluster` の契約さえ守っていれば、ビジネスロジックを大きく変えずに移行できます。
