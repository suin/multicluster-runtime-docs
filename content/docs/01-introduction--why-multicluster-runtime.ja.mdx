---
title: なぜ multicluster-runtime なのか？
---

現代の Kubernetes プラットフォームは、1つのクラスターだけで完結することはほとんどありません。分離（セキュリティ／テナント）、地理的な配置、スケール、コスト最適化、異なるコントロールプレーンなどの理由から、実際の環境は **複数クラスターのフリート** を扱うことが一般的です。`controller-runtime` はシングルクラスターのコントローラーを簡潔に書けますが、同じコードベースで多数のクラスターをリコンサイルしようとすると、いくつかのギャップが顕在化します。

`multicluster-runtime` は、このギャップを **controller-runtime のメンタルモデルを崩さずに** 埋めるために生まれました。この章では、このプロジェクトがなぜ存在するのか、どのような課題を解決するのか、そして他の選択肢とどう違うのかを説明します。

---

### マルチクラスターの課題領域

クラスター数が増えるにつれ、プラットフォームチームは次のような能力をコントローラーに求めるようになります。

- **変化し続けるフリートの検出と追跡**: クラスターは参加し、離脱し、プロパティが変化します。
- **各クラスター内イベントへのリアクティブな対応**: オブジェクトの監視、フィールドインデックスの作成、変更に対するリコンサイル。
- **必要に応じたクロスクラスター調整**: ロケーションやキャパシティに基づくスケジューリング、ヘルスの集約、設定のファンアウトなど。
- **既存の controller-runtime のワークフローを維持**: Manager / Builder / Reconciler / client を、そのまま再利用したい。

素の `controller-runtime` だけでこれを実現しようとすると、シングルクラスターでは見えなかった複雑さにすぐに突き当たります。

---

### 素朴なアプローチで起こりがちな問題

今日よく見られるマルチクラスターコントローラーの実装パターンには、次のようなものがあります。

- **各クラスターに1つずつコントローラーをデプロイする（クラシックなモデル）**  
  - 各メンバークラスターの中に、Manager / Cache / workqueue / Reconciler を含むフルスタックのコントローラーポッドを配置します。  
  - **欠点**:
    - クラスター数に比例して運用負荷が増大します。
    - アップグレードや設定変更、監視・ロギングの整備を多数のデプロイメントに対して行う必要があります。
    - クロスクラスターのロジックは別の調整レイヤーが必要になります。

- **1つのプロセス内に多数の Manager を立ち上げる**  
  - 1つの Pod の中で、対象クラスターごとに独立した `manager.Manager` を起動します。  
  - **欠点**:
    - 各 Manager が自前の cache / informer / workqueue / metrics を持つため、リソース使用量がクラスター数とともに悪化します。
    - 多数の Manager を跨いだ watch・reconciler の配線が複雑で、バグを生みやすくなります。

- **外部のプロセスマネージャーや独自フレームワークに依存する**  
  - クラスターごとにコントローラーバイナリを起動する supervisor を用意したり、controller-runtime とは別のマルチクラスター用フレームワークを採用したりします。  
  - **欠点**:
    - 追加のプロセスマネジメントプレーンを運用する必要があります。
    - 既存の controller-runtime のコードやナレッジを再利用しにくくなります。
    - 特定のコントロールプレーン技術に強く結びついた実装になりがちで、プロバイダー非依存ではありません。

これらのモデルでは、**Reconciler は「世界がシングルクラスターである」前提で書かれ**、クラスターの検出・ライフサイクル・ファンアウト・バックプレッシャーといったマルチクラスター固有の関心事は、別の場所で大量のカスタムコードとして処理されることになります。

---

### multicluster-runtime の設計目標

`multicluster-runtime` は、いくつかのコアな目標に基づいて設計されています。

- **controller-runtime を置き換えずに拡張する**  
  - 既存の Manager / Builder / Reconciler / Source のアーキテクチャをそのまま維持します。  
  - 独自 Manager への置き換えやフォーク、`go.mod` での replace に頼りません。

- **One Pod, Many Clusters**  
  - 単一のコントローラープロセスで、**動的に変化するフリート** に接続します。  
  - 各クラスターごとに専用の cache と client を持たせつつ、workqueue などはできる限り共有します。

- **Provider 駆動の検出とライフサイクル管理**  
  - 「クラスターはどこから来るのか？」をプラガブルな `multicluster.Provider` としてモデル化します。  
  - Cluster API、ClusterProfile、kubeconfig、Kind、ファイル、Namespace、インメモリリスト、それらの組み合わせなど、さまざまなインベントリソースをサポートします。

- **シングルクラスター Reconciler からの最小限の差分**  
  - `reconcile.Request` を `mcreconcile.Request` に置き換え、`mgr.GetCluster(ctx, req.ClusterName)` で正しいクラスターの client を取得するだけです。  
  - ビジネスロジック自体はほとんど変えずに、シングルクラスターとマルチクラスターの両方で同じコードを動かせます。

- **SIG-Multicluster の標準との整合性**  
  - **クラスター識別子**（KEP-2149）、**クラスターインベントリ**（KEP-4322）、**クレデンシャルプラグイン**（KEP-5339）を Provider の第一級の入力として扱います。  
  - これにより、各プロジェクトがクラスター ID／インベントリ／認証の仕組みを一から作り直すのではなく、標準 API の上にコントローラーを構築しやすくなります。

アーキテクチャの詳細やコード上の構成は別の章で扱います。ここでは、そのような設計が「なぜ」重要なのかに焦点を当てます。

詳細は: [01-introduction--architecture.md](01-introduction--architecture) を参照してください。

### multicluster-runtime がもたらす変化

`multicluster-runtime` では、最初に通常どおり `controller-runtime` の Manager から始め、それを **マルチクラスター対応の Manager** でラップし、さらに Provider を差し込みます。

- **マルチクラスターマネージャー**  
  - ホストクラスター用の通常の `manager.Manager` を内部に埋め込みます。  
  - 特定のメンバークラスターに対して動作するための `GetCluster` / `GetManager` / `ClusterFromContext` / `GetFieldIndexer` などを公開します。  
  - Provider がランタイムにクラスターを **Engage（参加）／Disengage（離脱）** できるように、`multicluster.Aware` インターフェースを実装します。

- **フリートアダプターとしての Provider**  
  - 各 Provider は、クラスターを検出し、それに対応する `cluster.Cluster` オブジェクトを構築する方法を知っています。  
  - 例:
    - Cluster API Provider: CAPI の `Cluster` リソースを読み取ります。
    - Cluster Inventory API Provider: `ClusterProfile` オブジェクトと KEP-4322/5339 に準拠したクレデンシャルプラグインを利用します。
    - Kind / Kubeconfig / File / Namespace Provider: ローカル開発、シンプルなデモ、Namespaces-as-Clusters によるシミュレーションなどをサポートします。
    - Multi / Clusters / Single / Nop Provider: プロバイダーの合成やテスト用のユーティリティです。

- **統一されたコントローラーパイプライン**  
  - Source や Handler の登録は一度だけ行い、**Engage された各クラスターごとにファンアウト** してイベントを収集し、それらを単一の論理的なコントローラーパイプラインへ流し込みます。  
  - Reconciler は `mcreconcile.Request{ClusterName, Request}` を受け取り、実行時に適切な `cluster.Cluster` を解決します。

これにより、**コントローラーを書き換えることなく、クラスター数の増加に応じてスケール** でき、Manager やプロセスを増やしていく必要もなくなります。

### 他のマルチクラスターアプローチとの比較

`multicluster-runtime` だけがマルチクラスターコントローラーを構築する方法ではありませんが、その立ち位置は次のように整理できます。

- **生の controller-runtime と自前配線との比較**  
  - 手作業で複数の `cluster.Cluster` インスタンスを作成し、それぞれの cache を管理し、イベントを 1 つのキューに多重化することは理論上可能です。  
  - `multicluster-runtime` は、こうしたパターンを Manager / Provider / Source / Builder として再利用可能なコンポーネントにまとめ、すべてのプロジェクトが同じ問題をゼロから解く必要がないようにします。

- **専用のマルチクラスター・フレームワークや管理プラットフォームとの比較**  
  - OCM、Clusternet、Fleet、Karmada などは、スケジューリング・プレースメント・ロールアウト・ポリシー・UI まで含んだフルな管理プレーンを提供します。  
  - `multicluster-runtime` はより低レイヤーに位置する **Go ライブラリ** であり、こうしたプラットフォームが提供する ClusterProfile ベースのインベントリ（KEP-4322）を Provider 経由で消費する側にもなり得ます。

- **他のマルチクラスターコントローラーライブラリとの比較**  
  - 一部のライブラリは、独自のコントローラー抽象や Manager を定義します。  
  - `multicluster-runtime` は、あくまで upstream controller-runtime の上に乗る **薄く汎用的な拡張** であることを重視しています。
    - 新たに学ぶべき Manager 型を増やしません。
    - `ClusterName` が追加される以外に、独自の workqueue や Reconciler パターンを導入しません。
    - 既存のコントローラーやエコシステムツールの移行・共有を容易にします。

すでに controller-runtime を使っていて、運用対象をフリートにまで広げたい場合、`multicluster-runtime` は「ネイティブな道筋」に近い選択肢となるよう設計されています。

### multicluster-runtime がフィットする場面

次のようなケースでは、`multicluster-runtime` の恩恵を受けやすくなります。

- **controller-runtime でコントローラーを書いており、その延長としてマルチクラスターを取り込みたい**。
- **数十〜数百のクラスター** を管理しており、単一のコントローラーバイナリでそれらを観測・操作したい。
- **均一なロジックとクロスクラスターなロジックの両方が必要**:
  - 全クラスターに対するポリシー適用やベースラインリソースの維持。
  - ワークロード・証明書・設定のクロスクラスターオーケストレーション。
- **標準化されたインベントリとアイデンティティと統合したい**:
  - `ClusterProfile` ベースのインベントリや ClusterSet を消費したい。
  - 環境ごとの認証ロジックを Reconciler に埋め込むのではなく、クレデンシャルプラグイン（KEP-5339）を活用したい。

---

### multicluster-runtime を使わなくてもよい場面

すべてのコントローラーに `multicluster-runtime` が必要というわけではありません。

- **純粋なシングルクラスターコントローラー**  
  - 今後も 1 つのクラスターだけで動かす前提であれば、素の `controller-runtime` が最もシンプルです。  
  - 後からマルチクラスター化する場合も、差分を小さく保てるように設計されています。

- **Go や controller-runtime を使っていないプロジェクト**  
  - 利用言語やフレームワークが異なる場合、このライブラリを直接使うことはできません（ただし、ここで紹介されるアーキテクチャパターン自体は参考になるかもしれません）。

- **すでにフル機能のマルチクラスター管理プラットフォームに完全依存している場合**  
  - そのプラットフォームが提供するコントローラーだけで要件が満たされ、自作コントローラーを書く予定がないなら、`multicluster-runtime` を導入する必要はありません。

---

### SIG-Multicluster とエコシステムにとっての意味

`multicluster-runtime` は、進化しつつある Kubernetes のマルチクラスター標準と、日々コントローラーを書く開発者との間をつなぐ **実践的なブリッジ** として、SIG-Multicluster のもとで開発されています。

- **クラスター識別（KEP-2149）** を、`ClusterName` の安定したキーとして扱います。
- **クラスターインベントリ（KEP-4322）** を、Provider が消費する **ClusterProfile API** として利用します。
- **クレデンシャルプラグイン（KEP-5339）** を通じて、クラウド固有ロジックを Reconciler に埋め込まずに、各メンバークラスター向けの `rest.Config` を取得します。

このように共通の API の上にマルチクラスターコントローラーを構築することで、`multicluster-runtime` を使って今日書いたコントローラーが、将来のスケジューラや管理プレーン、各種ツールと連携しやすくなりつつ、慣れ親しんだ controller-runtime の開発体験を手放さずに済むようになります。
